# Writing a clean body is NOT enough — the footer is appended after you

Writing no attribution is only half the job. The `mcp__github__*` write tools
APPEND a `---` rule followed by an italic "Generated by" line linking
`claude.ai/code` to the body **server-side, after your text leaves you**. The
harness prompt even admits it ("the server strips duplicate footers before
posting"). So a PR body you wrote perfectly clean still lands on GitHub
carrying an AI byline, and you will not see it unless you go and look.

This is not theoretical: it shipped on a PR and the USER found it, not me.

**It is not only the `mcp__github__*` tools.** This was first recorded as an
MCP-server behaviour with two escapes — use the env token, or strip it with an
update. Measured again on 2026-09-05, **both escapes are gone**: a `POST`
straight to `api.github.com` with `$GITHUB_TOKEN` came back carrying the
footer, and a `PATCH` sending the exact intended body came back carrying it a
second time. Read the two numbered steps below as history plus a correction,
not as a recipe.

## What to do, every time

1. **Try the env token first — but check the result, because it is no longer a
   clean path.** `$GITHUB_TOKEN` / `$GH_PERSONAL_ACCESS_TOKEN` are real and the
   call succeeds:

       TOKEN="${GITHUB_TOKEN:-$GH_PERSONAL_ACCESS_TOKEN}"
       curl -s -X POST -H "Authorization: Bearer $TOKEN" \
         -H "Accept: application/vnd.github+json" \
         https://api.github.com/repos/<owner>/<repo>/pulls -d @body.json

   **Measured 2026-09-05 on future-pay#1488: the footer was appended anyway.**
   The gateway intercepts `api.github.com` and appends server-side regardless of
   which token authenticates the call, so "use the env token" is no longer a way
   to avoid it. Read the body back and see for yourself rather than assuming.

2. **If that 403s, it is the SESSION GATEWAY, not a bad token.** In Claude Code
   web/remote sessions `api.github.com` is intercepted and answers
   `{"message":"GitHub access is not enabled for this session…"}`. Do not retry
   and do not route around it. `git push` over HTTPS keeps working — only the
   REST API is gated. Fall back to step 3.

3. **Write → read back → try ONE strip → then stop.** After ANY create or
   comment call, re-read the object and look for the footer.

   **An `update_*` re-appends it. Do not spend a second cycle on this.** The
   older advice here said updates were safe — "verified" — and that is now
   false. On future-pay#1488 the body was written clean through the REST API
   with the env token, came back with the footer, was `PATCH`ed with the exact
   intended body, and came back with the footer a second time. Both writes went
   through `api.github.com` directly, not through an `mcp__github__` tool.

   So from a session behind this gateway the footer cannot be removed. Try the
   strip once, and if it survives, **say so in your report** rather than
   retrying or quietly leaving an AI byline on the PR without telling anyone.
   The rule in `no-ai-attribution` still stands for everything you author; what
   has changed is that compliance is no longer fully in your hands, and the
   honest move is to name the gap.

## A COMMENT cannot be cleaned. Do not post one you would have to strip.

Step 3 only works where an `update_*` tool exists. It does for PR and issue
BODIES. It does **not** for issue/PR comments: the MCP surface offers
`add_issue_comment` and no edit or delete. So a comment posted through it keeps
the appended footer permanently, and the only fix is a human deleting it.

Therefore, for anything you author yourself — CI status, a blocker, a
finding — **put it in the PR body and update that**, which you can verify
clean. Reserve comments for the case where a reply genuinely must sit in the
thread (answering a reviewer), and accept the footer there as the cost of
replying at all.

## Scope

Every body that lands on GitHub: PR bodies and titles, issue bodies, issue
comments, review bodies, review replies — and anything else a tool posts on
your behalf.
